모바일 애플리케이션 모의해킹

THE GALLERY APP을 대상으로 모바일 애플리케이션과 API 서버의 인증·인가, 통신 구간 및 민감정보 처리 영역을 점검하고 취약점 재현부터 보안 조치와 검증까지 수행했습니다.

대상
THE GALLERY APP · app-debug.apk
환경
Android Emulator API 35 · Kali Linux
도구
MobSF · Burp Suite · Wireshark · jwt.io · SQLite Viewer
기간
2025.12.01 ~ 2025.12.23
1

모의해킹 수행 배경

최근 국내 대형 이커머스 기업에서 발생한 개인정보 유출 사고를 참고하여, 유사한 보안 위협을 실증적으로 분석할 수 있는 가상의 서비스 환경을 구축했습니다.

THE GALLERY APP이라는 가상의 미술품 온라인 판매 플랫폼을 설정하고, 해당 플랫폼의 모바일 애플리케이션과 API 서버를 대상으로 모의해킹을 수행했습니다. 실제 온라인 판매 플랫폼에서 발생할 수 있는 보안 위협을 가정하여 애플리케이션의 인증 및 인가 체계, 데이터 처리 방식, 정보 저장 및 전송 과정에서 발생할 수 있는 취약점을 점검했습니다.

진단 목적

특히 API 인증 결함(JWT)과 과도한 데이터 노출(Excessive Data Exposure) 취약점이 결합되었을 때, 단순한 권한 상승을 넘어 다수의 회원 정보가 노출될 수 있는 공격 시나리오를 재현하고 보안 개선 방안을 검증하는 데 목적을 두었습니다.

2

모의해킹 수행 대상

API 인증 결함(JWT)과 과도한 데이터 노출이 결합되는 상황을 실증적으로 분석하기 위해 진단을 수행했습니다.

  • A
    애플리케이션: THE GALLERY APP (app-debug.apk)
  • S
    API 서버: Node.js Backend Server(http://192.168.16.12:3000)
  • E
    테스트 환경: Android Emulator(API 35) · Kali Linux(Burp Suite, Wireshark, Suricata)
  • P
    수행 역할: 모바일 앱 취약점 진단 및 서버 보안 설정 검증
    • 3

    진단 결과 요약

    통신 암호화 미적용, JWT 서명 키 관리 미흡 및 토큰 위조 가능성, API 응답과 로컬 저장소 내 민감정보 노출이 확인되었습니다.

    구분취약점주요 확인 내용위험도

    1

    M5 · Insecure Communication

    HTTP 평문 전송 및 주요 정보 노출
    High

    앱과 서버 간 통신에 암호화되지 않은 HTTP가 사용되며 SSL/TLS(HTTPS)가 적용되지 않았습니다.

    Wireshark와 Burp Suite를 이용한 네트워크 패킷 감청 결과 로그인 후 발급된 JWT와 요청 헤더의 토큰 값이 평문으로 노출되는 것을 확인했습니다.

    -> 공격자가 이를 탈취할 경우 사용자 인증 없이 세션 하이재킹이 가능합니다.

    실제 수행 캡
    이미지를 클릭하면 원본 크기로 확대해서 확인할 수 있습니다.
    1
    로그인 요청 확인
    HTTP 기반 통신에서 인증 과정의 패킷을 확인했습니다.
    2
    JWT 노출 확인
    서버가 발급한 인증 토큰이 평문 상태로 전송되는 것을 확인했습니다.
    3
    영향 확인
    탈취한 토큰을 재사용하여 정상 사용자로 위장하는 세션 하이재킹 가능성을 확인했습니다.
    2

    M3 · JWT 토큰 위조 및 권한 상승

    취약한 Secret 및 서버 측 권한 검증 부재
    Medium

    JWT 서명에 사용되는 비밀키가 단순 문자열로 하드코딩되어 있고, 서버가 실제 권한 검증 없이 토큰 내용을 신뢰하는 구조가 확인되었습니다.

    실제 수행 증적
    이미지를 클릭하면 원본 크기로 확대해서 확인할 수 있습니다.

    단계 1 · 일반 사용자 토큰 획득

    Payload: {"username": "woowow", "level": "SILVER", ...}

    단계 2 · 토큰 위조

    username → admin level → GOLD 취약한 Secret을 이용해 Signature 재생성

    단계 3 · 위조 토큰 적용

    Burp Suite로 요청을 가로채 재생성한 토큰 삽입 → 앱 새로고침 후 서버가 위조 토큰을 유효한 관리자 토큰으로 인식

    단계 4 · 권한 상승 확인

    [Auto Login] Welcome back, admin → GOLD CLASS 및 관리자 전용 기능 접근 성공
    3

    M1 · Improper Credential Usage

    API 응답 및 로컬 저장소 내 민감정보 노출
    Medium

    GET /verify-token 응답에 평문 비밀번호가 포함되어 있었으며, JWT 토큰 및 사용자 정보가 AsyncStorage에 평문으로 저장되는 것을 확인했습니다.

    실제 수행 증적
    이미지를 클릭하면 원본 크기로 확대해서 확인할 수 있습니다.
    1
    API 응답 분석
    로그인 및 토큰 검증 API 응답에 사용자의 평문 비밀번호가 포함됨을 확인했습니다.
    2
    로컬 저장소 분석
    SQLite Viewer로 RKStorage를 확인한 결과 auth_token 값에 토큰이 그대로 저장되어 있었습니다.
    1

    M5 · HTTPS 및 TLS 적용

    • 1
      애플리케이션과 서버 간 모든 통신 채널에 SSL/TLS(HTTPS) 적용
    • 2
      AndroidManifest.xml에서 android:usesCleartextTraffic="false" 적용
    • 3
      SSL Pinning을 적용하여 지정된 인증서 외 연결 차단
    검증 결과

    모든 트래픽이 TLS로 암호화되어 전송되며 TLSv1.3 사용 및 Application Data 암호화를 확인했습니다.

    실제 수행 증적
    이미지를 클릭하면 원본 크기로 확대해서 확인할 수 있습니다.
    2

    M3 · JWT Secret 키 관리 개선

    BEFORE
    단순 문자열 Secret 하드코딩 → 토큰 위조 가능
    AFTER
    256비트 이상 난수 키 → .env 환경변수로 분리 관리
    1
    강력한 Secret 적용
    Node.js 서버의 .env에 난수로 생성한 비밀키를 적용했습니다.
    2
    위조 JWT 재검증
    기존 취약한 키로 서명된 위조 JWT를 전송했습니다.
    3
    차단 확인
    jwt.verify에서 서명 불일치 오류가 발생하고 403 Forbidden으로 요청이 차단됨을 확인했습니다.
    실제 수행 증적
    이미지를 클릭하면 원본 크기로 확대해서 확인할 수 있습니다.
    3

    M1 · API 응답 및 로컬 저장소 보호

    ① API 응답 DTO 적용

    BEFORE
    DB 원본 데이터를 그대로 응답 → password 노출
    AFTER
    toUserResponseDTO() → password 필드 제거 후 전송

    ② 로컬 저장소 암호화

    BEFORE
    AsyncStorage 평문 JWT 저장
    AFTER
    react-native-encrypted-storage Android Keystore 연동 · AES-256 암호화
    검증 결과

    기존 RKStorage 파일에서 토큰 정보가 더 이상 평문으로 저장되지 않으며, 설정 파일의 Key/Value가 판독 불가능한 암호문으로 저장됨을 확인했습니다.

    실제 수행 증적
    이미지를 클릭하면 원본 크기로 확대해서 확인할 수 있습니다.
